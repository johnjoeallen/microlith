    The eight modes compared¶

    Same code, same API, same tests, same workload, and (except split-dbs) the same single PostgreSQL instance: the eight-process modes share one database server, so the comparison measures the cost of the process boundary, not of separate databases. Four concurrent clients, 1,200 measured orders per run, result cache on, parallel quotes on, follow-ups through the outbox (method).

    "Calls by binding" counts every module-to-module call in the run and gives its mean latency. A call answered by the result cache has binding cache; a call between modules in the same process is local; the other bindings are described in the architecture.

    What the numbers say¶

    In one process, the module boundary is almost free¶

    • modulith and macro-monolith are the same thing built two ways, and they measure the same (336 and 331 orders/s).
    • loopback-codec forces every call through JSON encoding and decoding, in memory: 93% of the throughput, median 12.4 ms against 11.6 ms. Serialisation is a small tax, and it is the price of proving that no object identity or shared transaction crosses a boundary.
    • loopback-http makes every call a real HTTP request to the same process: 71% of the throughput and a median of 16.3 ms. The cost of the protocol, without a second JVM, is already 29% of the throughput.

    Between processes, the price is paid per call¶

    • Three processes (groups): 67% of the throughput, median 17.4 ms. Calls inside a group stay local at about 0.5 ms, calls between groups cost 1.7 ms.
    • Eight services (microservices): 49%, median 22.7 ms, and every call is remote at about 2.0 ms.
    • split-dbs equals groups (230 against 225 orders/s): putting each group on its own PostgreSQL instance cost nothing measurable here. (On one machine the database servers do not compete for the same network link; across real hosts it would.)
    • microservices-macro, the same eight processes built from the single macro jar, matches microservices (178 against 166, inside the run-to-run noise). The one-artifact claim costs nothing at runtime.

    A single p99 outlier

    microservices shows p99 77 ms against 44.7 ms for microservices-macro. That is one slow stretch in one run, not a property of the shape; compare the p50 and p95 columns, which agree.

    Where the time goes¶

    Mean latency of the most expensive module-to-module calls, over all bindings used:

    Call (mean ms, all bindings) modulith loopback-codec loopback-http groups microservices

    orders -> shipping.createShipment 1.62 1.74 2.35 2.31 3.34
    orders -> inventory.reserve 1.43 1.53 1.74 2.09 2.27
    orders -> payments.authorize 1.00 1.10 1.68 1.75 2.72
    orders -> pricing.quote 0.78 0.88 1.70 1.91 2.85

    orders -> notifications.send 0.79 0.88 1.59 1.21 2.58
    orders -> payments.capture 0.62 0.67 1.02 1.25 1.47
    shipping -> inventory.getReservation 0.35 0.43 0.76 0.42 1.12
    orders -> customers.getCustomer 0.22 0.27 0.53 0.67 0.74

    Read across a row: orders -> shipping.quote takes 1.16 ms inside one process and 4.35 ms between eight services. Reading down the table shows that a "local" call is not free either: even in modulith each call is one database query, which is why the expensive rows (quote, create shipment, reserve) are the ones that do the most work.

    Choosing¶

    If you value... Pick
    The best latency and throughput modulith (or macro-monolith, equal)
    A boundary that is proven to hold, at 7% cost loopback-codec as a test configuration
    A few deployable units with most of the speed groups: two thirds of the monolith's throughput with three processes instead of eight
    Independent deployment and scaling of every module microservices or microservices-macro, at about half the throughput on this machine

    groups is the interesting middle: it keeps the chatty chains (pricing → catalog, shipping → inventory → catalog) inside one process, so those calls stay at local cost.
