    The eight modes compared¶

    Same code, same API, same tests, same workload, and (except split-dbs) the same single PostgreSQL instance: the eight-process modes share one database server, so the comparison measures the cost of the process boundary, not of separate databases. Sixteen concurrent clients, 1,500 measured orders per run, result cache on, parallel quotes on, follow-ups through the outbox, a VACUUM ANALYZE after the warm-up (method). The charts and the first table are means over 5 runs; the table under "All numbers" is the first of those runs, which also holds the call counts.

    Mode Orders/s Share of modulith Median order (p50) p99
    modulith 445 100% 34.2 ms 60.5 ms
    macro-modulith 442 99% 34.3 ms 63.4 ms
    loopback-codec 434 98% 35.2 ms 60.2 ms
    loopback-http 312 70% 48.1 ms 77.6 ms
    groups 247 56% 62.2 ms 98.7 ms
    split-dbs 250 56% 61.0 ms 98.2 ms
    microservices 159 36% 96.9 ms 181.9 ms
    microservices-macro 156 35% 98.4 ms 177.4 ms

    0 of 40 mode runs were dropped as outliers.

    The median is not the time one order takes alone: with 16 clients the orders queue behind each other, so the median is roughly clients ÷ throughput.

    What the numbers say¶

    In one process, the module boundary is almost free¶

    • modulith and macro-modulith are the same thing built two ways, and they measure the same (445 and 442 orders/s).
    • loopback-codec forces every call through JSON encoding and decoding, in memory: 98% of the throughput, median 35.2 ms against 34.2 ms. Serialisation is a small tax, and it is the price of proving that no object identity or shared transaction crosses a boundary.
    • loopback-http makes every call a real HTTP request to the same process: 70% of the throughput and a median of 48.1 ms. The cost of the protocol, without a second JVM, is already 30% of the throughput.

    Between processes, the price is paid per call¶

    • Three processes (groups): 56% of the throughput, median 62.2 ms. Calls inside a group stay local at about 0.4 ms, calls between groups cost about 1.5 ms.
    • Eight services (microservices): 36%, median 96.9 ms, and every call is remote at about 2.2 ms.
    • split-dbs equals groups (250 against 247 orders/s): putting each group on its own PostgreSQL instance cost nothing measurable here. (On one machine the database servers do not compete for the same network link; across real hosts it would.)
    • microservices-macro, the same eight processes built from the single macro jar, matches microservices (156 against 159, inside the run-to-run noise). The one-artifact claim costs nothing at runtime.

    Where the time goes¶

    Mean latency of the most expensive module-to-module calls, over all bindings used:

    Call (mean ms, all bindings) modulith loopback-codec loopback-http groups microservices
    orders -> shipping.quote 0.70 0.74 1.80 1.89 4.69
    orders -> shipping.createShipment 1.14 1.17 1.72 1.96 3.52
    orders -> inventory.reserve 1.20 1.18 1.47 1.97 2.35
    orders -> payments.authorize 0.75 0.78 1.24 1.76 2.95
    orders -> pricing.quote 0.44 0.47 1.05 1.60 3.46
    shipping -> inventory.getStock 0.25 0.25 0.57 0.33 1.55
    orders -> notifications.send 0.58 0.62 1.09 0.92 2.47
    orders -> payments.capture 0.52 0.53 0.79 1.20 1.52
    shipping -> inventory.getReservation 0.27 0.29 0.55 0.37 1.11
    pricing -> customers.getCustomer 0.14 0.15 0.30 0.64 0.89
    orders -> customers.getCustomer 0.14 0.15 0.34 0.59 0.78
    shipping -> customers.getCustomer 0.07 0.07 0.15 0.32 0.38

    Read across a row: orders -> shipping.quote takes 0.70 ms inside one process and 4.69 ms between eight services. Reading down the table shows that a "local" call is not free either: even in modulith each call is one database query, which is why the expensive rows (quote, create shipment, reserve) are the ones that do the most work.

    One database instance or one per deployable unit¶

    Everything above ran on one shared PostgreSQL instance. --dbs split gives every deployable unit its own instance, which is three for groups and eight for the services (how); the one-process modes have one unit, so nothing changes for them. The same load, cache on, parallel quotes on, outbox (the full matrix has the other combinations, which agree):

    Mode orders/s shared split Δ p50 shared split Δ p99 shared split Δ
    groups 245 245 -0% 62.7 63.0 +0% 103.2 115.1 +11%
    microservices 161 159 -1% 96.4 96.1 -0% 174.0 179.8 +3%
    microservices-macro 161 157 -2% 94.4 97.5 +3% 170.7 174.0 +2%

    One run per cell, so these are within noise: on this machine, with the database servers sharing the same CPUs and memory and the same loopback, giving each unit its own server cost nothing measurable. A real split adds what one machine cannot show: network latency to each database, and a server per service to provision, secure, back up and size. Treat it as a floor (where the evidence stops).

    Choosing¶

    If you value... Pick
    The best latency and throughput modulith (or macro-modulith, equal)
    A boundary that is proven to hold, at 2% cost loopback-codec as a test configuration
    A few deployable units with most of the speed groups: more than half of the monolith's throughput with three processes instead of eight
    Independent deployment and scaling of every module microservices or microservices-macro, at about a third of the throughput on this machine

    groups is the interesting middle: it keeps the chatty chains (pricing → catalog, shipping → inventory → catalog) inside one process, so those calls stay at local cost.
