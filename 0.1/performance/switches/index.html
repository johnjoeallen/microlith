    Cache, parallel quotes and follow-up delivery¶

    Three optional features, each with an off-switch, each measured by running the same workload with the switch off and on. Same conditions as the mode comparison: 16 clients, 1,500 measured orders, deterministic order stream.

    Result cache¶

    @Cached lets four read methods (customers.getCustomer, customers.getPaymentMethod, catalog.getProduct, catalog.productExists) reuse their result for 30 seconds. Every mode, cache off against on:

    Mode orders/s off on Δ p50 off on Δ p99 off on Δ
    modulith 432 444 +3% 35.6 33.9 -5% 54.3 82.6 +52%
    macro-modulith 435 446 +3% 35.4 34.0 -4% 55.4 53.3 -4%
    loopback-codec 419 444 +6% 36.9 34.6 -6% 53.9 50.2 -7%
    loopback-http 281 315 +12% 53.9 47.6 -12% 85.1 77.6 -9%
    groups 233 248 +6% 65.2 62.1 -5% 108.0 100.1 -7%
    split-dbs 238 255 +7% 64.4 60.2 -7% 106.1 93.5 -12%
    microservices 135 160 +19% 112.2 96.1 -14% 227.4 180.9 -20%
    microservices-macro 136 160 +18% 111.9 97.5 -13% 205.0 176.1 -14%

    What it shows

    • The more a call costs, the more a hit saves. In the split modes the cache adds 6 to 19% throughput and takes 5 to 14% off the median order. In a single process the same cache adds 3 to 6%.
    • Read differences of about 5% as noise: modulith and macro-modulith are the same code and both show +3%.
    • About 30% of all calls in a run were answered by the cache (8,994 of 29,919 in modulith). A hit costs 0.00 to 0.01 ms.

    Hit rates (share of calls to each method answered from the cache, whole run):

    Cached method modulith macro-modulith loopback-codec loopback-http groups split-dbs microservices microservices-macro
    catalog.getProduct 78% 78% 78% 78% 78% 78% 78% 78%
    catalog.productExists 78% 78% 78% 78% 78% 78% 78% 78%
    customers.getCustomer 50% 50% 50% 51% 51% 51% 46% 46%
    customers.getPaymentMethod 35% 35% 35% 35% 35% 35% 35% 35%

    The rates are moderate because the runs are short (a few seconds for 1,500 orders), the keys are spread over 10,000 customers, and each of the eight processes in the two eight-service modes warms its own cache (the customer rate falls from 50% to 46% there). A longer run would raise them; the 30-second time-to-live was not the limit here.

    Parallel quotes¶

    Parallel quotes run the customer check and the two quotes at the start of placeOrder at the same time instead of one after the other. Sequential against parallel, for the modes where calls cost something (the cache is on in both):

    Mode orders/s off on Δ p50 off on Δ p99 off on Δ
    modulith 454 451 -0% 33.0 33.0 +0% 54.6 85.2 +56%
    loopback-http 301 326 +8% 49.8 46.3 -7% 83.0 73.7 -11%
    groups 230 253 +10% 66.3 60.4 -9% 140.9 96.0 -32%
    split-dbs 247 253 +3% 61.7 61.1 -1% 102.9 99.5 -3%
    microservices 138 160 +15% 110.1 96.0 -13% 217.5 170.1 -22%
    microservices-macro 138 161 +17% 108.6 95.3 -12% 211.1 167.6 -21%

    What it shows

    • It helps in proportion to how slow the calls are: nothing measurable in one process, +8% over HTTP to itself, +3 to 10% with three processes (split-dbs and groups, which disagree, so read it as a range), +15 to 17% with eight services. The median order falls by 0%, 7%, 1 to 9% and 12 to 13% respectively.
    • The effect is predictable from the per-call table: in microservices the three reads cost 0.78 + 3.46 + 4.69 = 8.9 ms one after the other and about 4.7 ms together (mean latencies, single run), a saving of about 4 ms per order. At 16 clients the median also contains queueing, so the fall in the median (110 to 96 ms) is not a simple sum of the saving.
    • It removes waiting, not work. It does not make the machine do less, so the gain shrinks when the machine is saturated.

    Follow-up delivery: outbox or events¶

    Follow-ups (the confirmation message, the release of a reservation, the voiding of a payment) are made durable in the order's transaction and delivered afterwards, either by the outbox relay or as Spring Modulith events. On the request path:

    Mode orders/s outbox events Δ p50 outbox events Δ p99 outbox events Δ
    modulith 451 439 -3% 33.0 34.4 +4% 85.2 57.9 -32%
    groups 253 244 -4% 60.4 63.2 +5% 96.0 105.2 +10%
    microservices 160 150 -6% 96.0 102.5 +7% 170.1 173.8 +2%

    What it shows

    • In one process the two are within noise (451 against 439 orders/s, outbox against events).
    • Events were 3 to 6% lower in throughput in this run (in every mode) and the median order 4 to 7% higher. The cause was not investigated (the registry's extra status updates and the asynchronous executor are candidates). It is a small cost, close to the run-to-run noise. Events run inside the same JVM as the orders, so the cost can be expected to grow with the order rate; the outbox moves that work to a table and a relay that can be tuned.
    • The p99 swings both ways (modulith 85.2 against 57.9 ms, groups 96.0 against 105.2) and is one slow stretch in one run; the p50 and p95 do not move with it.
    • Where the two really differ is how quickly the follow-ups are delivered, which a round-trip measurement cannot see. That is the next page.
